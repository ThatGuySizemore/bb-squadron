# Workers in a lane

The bound Lead calls `squadron_spawn_worker` with a ticket identifier. The Helper refreshes the Linear mirror, reads the project's settings, asks the deterministic core for a frontier decision, and reserves the ticket before calling BB. Per-lane commands are serialized, so concurrent calls cannot exceed the worker cap or start the same ticket twice. Merely reading the board never launches a worker.

A worker is a real child of the saved Lead, in a managed worktree cut from that lane's integration branch. Its label route, or the owner's saved card override, sets provider, model and effort. Permission mode remains `auto` and service tier remains `default`, following B1's current conventions. Worker instructions require `tdd` and merging the latest integration tip into the worker's own branch before reporting done. The Lead owns merging into the integration branch and opening or merging the spec PR. UI work also uses impeccable. SDK metadata records the role, lane and ticket for links and later reconstruction. It grants no tool authority.

## First prompt and tool authority

BB resolves tools when the provider session starts. Lead, worker, reviewer and planning spawns therefore schedule their first prompt, save their trusted bindings, and explicitly release the queued prompt. Scheduled spawns have no environment yet. Provisioning later supplies the actual environment, so a null environment is preserved and refreshed, never invented.

`bb.agents.configure` selects tools from durable service records. The saved Lead gets worker/reviewer spawn, report and status. A saved worker or reviewer gets report and status. A saved reviewer also gets the bundled `squadron-reviewer` skill before its first prompt is released. Planning tools come from the outbox's saved grant; the planner skill comes from its saved planning session. Unbound threads get no tools even if they copy Squadron metadata. Tool execution checks the real thread's project, lifecycle, environment and worker parent again, and requires the lane's original Linear workspace and binding.

A plugin dispatch hook rejects a queued Squadron-origin launch whose service binding is missing, stopped or failed. If first-prompt release fails, the same known thread stays visible with its reason and reserved slot; its future schedule cannot silently start it through the automatic dispatcher. BB's explicit user Send-now override remains BB's own policy. Full interrupted-spawn reconstruction and resumed queue recovery belong to B8.

## Questions

A working worker in a flying lane can ask the owner with `squadron_report` `{ type: "question", text }`. The Helper saves it on the worker record, the card reads Needs you, and the question appears in Needs you with Answer in thread. The worker finishes its turn; the rest of the lane keeps going. While the question is open, the worker can't report done or ask a different question. Only the owner's own message reaching that worker thread clears it: a user initiator with no sender thread and no plugin origin. The Helper reads that from BB's `message.dispatch` checkpoint and from the `message.dispatched` event of a queued row. The event covers the owner's Send-now, which skips the checkpoint; BB supplies the thread's project before the binding is read. Messages from the Lead, the worker, Squadron or BB itself never answer for the owner. BB doesn't replay events missed while the plugin is down, so an answer sent then is caught only by the owner's next message. The Lead can't ask through this tool.

## Reports and integration

A worker reports `done` with its full commit SHA and test summary. The host verifies that its saved branch points to that exact commit. The report is saved and sent to the bound Lead as quoted data. Its card reads `Reported done`, uses the worker's route and opens the worker thread. It does not claim a reviewer exists. Before a reviewer starts, a changed, verified done commit replaces the earlier report. Once review starts, a changed commit requires the authorized fix round; it cannot inherit the earlier approval. Repeated reports of the same commit preserve status keys and avoid another confirmed Lead notification. A notification failure keeps the report and asks the worker to retry.

After the bound other-family reviewer approves and the Lead merges the work, the Lead reports `integrated` with the ticket and the same commit. The host verifies both the exact worker head and that the lane's integration branch contains it, checking the refs again for movement. Only then does the record carry verified integration progress and the card show `In branch`. The Helper independently requires approval from the saved other-family reviewer on that exact worker commit. Worker completion, Git ancestry and editable `pluginMetadata` do not grant approval. The core uses the same approval rule before it resolves a same-lane blocker.

A same-lane blocker can be satisfied by this verified integration record before the final PR marks every ticket Done in Linear. Done or canceled in Linear resolves a blocker for Ready, dispatch and cards. A blocker from another spec or project requires that Linear resolution; another lane's integration progress does not resolve it. A missing endpoint remains unresolved everywhere, displayed as `Unknown blocker` without exposing its relation UUID. Internal ordering is separate from the Ready row's outside blockers: a spec can start when part of its frontier is available, while its workers still wait for their own blockers. This is SIZE-932's added acceptance item.

The Helper queues In Progress when the child is started, then In Review after verified integration. A team using the manual lane's existing Waiting to Merge state uses that state when In Review is absent; the Helper never creates a workflow state. It never marks a ticket Done here. Status and signed Worker-comment writes use stable per-worker keys and the original expected workspace. Refused writes preserve the child and its work, carry a visible write reason, and can be retried by repeating the report. Returned receipt IDs establish queuing only; the outbox owns pending, blocked and delivered states.

`squadron_status` reads the lane and its cards plus saved commit reports, integration evidence and receipt IDs. The Lead sees the lane's reports; a worker or reviewer sees only its bound ticket's report and review. It grants no write capability.

## Per-ticket review

The Lead calls `squadron_spawn_reviewer` with `ticketId` after the verified done report. The Helper checks the actual worker's saved project, parent, environment and provider, verifies HEAD again, and starts a fresh thread from the other family in the worker's checkout. It uses `claude-opus-5-5` or `gpt-6.1-sol`, high effort and default service tier. The reviewer stays read-only. Its scheduled first prompt is released only after its trusted binding exists. Failed startup retains the binding and a visible reason; metadata cannot recover verdict authority.

Only that bound reviewer may report `type: verdict` with `commit`, `outcome: approve|changes`, `findings` and `resolvedFindingIds`. A stale or mismatched SHA is ignored without progress. The host rechecks exact worker HEAD before accepting a verdict; only a matching approved verdict plus B2's ancestry proof accepts integration. Repeating an identical verdict retries its notification without changing the verdict. A different verdict on the same reviewed commit is refused.

Each finding has a stable `id`, `kind` and `text`. `in-spec` includes missing or partial requirements and requires a fix. Only a `smell` may set `disposition`; it requires a fix unless the reviewer supplies `disposition: drop` and a single-line reason in text, 1 to 300 characters. `question` and `not-proven` remain in the report for the Lead to carry into the PR's Open questions and Not proven sections. Only `outside-spec` is eligible for defect filing. The Helper validates these declared categories; classification is the reviewer's technical judgement, not an automatic authority or owner approval.

The Lead requests the one fix round with `squadron_report({type: "fix", ticketId})`. Under the same per-lane queue as frontier dispatch, the Helper refreshes settings and blockers, rechecks the configured worker cap and verifies the original worker is idle and still bound. It reserves that worker as working **before** any SDK send. A full cap refuses the fix with no send, retry or queued release. New spawns and fix resumes cannot claim the same last slot. The reservation remains until the corrected report makes the worker idle again. An ambiguous send keeps the reservation for recovery rather than retrying a potentially live worker. Squadron-origin dispatch to a reported/integrated worker is refused until an authorized reservation marks it working.

The corrected worker reports a new verified SHA. The Lead calls `squadron_spawn_reviewer` again; it sends the one second look to the original reviewer with the corrected SHA and immutable first finding list. It creates no new reviewer. While a corrected report waits for the Lead to start the second look, its card reads Awaiting second look. The second look may only resolve or retain first-review IDs and kinds, and approval must resolve every first-review fix finding. A second changes verdict cannot start another fix round. Further strike/stop handling belongs to the lifecycle/limits tickets; no successor is unblocked by an unresolved review.

For a recorded `outside-spec` finding, the Lead first checks all project issues, including existing follow-ups, and reports `type: defect`, `ticketId`, `findingId`, `title`, `description`, a stable semantic `dedupeKey`, and `dedupeEvidence`. Supply `existingIssueId` for a matching issue. The Helper rejects in-spec findings, refreshes the mirror, checks exact normalized titles in both the mirror and saved defect records as well as saved semantic keys, and queues a new issue with only `needs-triage` when none matches. Saved records retain normalized titles and their Linear project. Defect commands share a project queue across lane commands so a queued issue can be reused before mirror catch-up, even with another ticket or key. This spec and its own tickets cannot be reused as outside defects by title or explicit ID. Semantic duplicate checking remains the Lead's responsibility. Retry the same payload after a refusal. The stable outbox keys retain the first queued issue even if saving its receipt was interrupted.

A Helper-only `related` outbox operation links the defect to its spec without turning it into a spec ticket. Delivery reads both relation directions, including archived pages, before creating the link. It reuses an existing related link and parks conflicting blocker/duplicate links as a visible conflict instead of replacing them. The read and mutation are separate Linear requests, so concurrent external relation edits are not an atomic guarantee. Issue and link receipts prove queuing only, never live delivery.

## Cards and routes

Ready and blocked tickets with route choices and no worker thread show a native model/effort selector. Saving disables the selector and announces `Saving route…`. A failed request shows a toast, and the board refreshes after the request. Once the Helper reserves a worker, the route is locked on the server as well as the card. Working cards open their actual worker thread. Review cards show the saved reviewer AI, review stage and reviewer thread. An unconfirmed reviewer has no navigation control; no model is inferred from the worker for a live review. Existing BB theme tokens, square pegs, dither, focus treatment and reduced-motion rules remain in place.

## Service seams and limits

- `LaneRun.workers` and `routeOverrides` are optional durable fields; B1 records remain valid. B1's nullable links, continued provisioning, start receipt IDs and `reconcileStart` remain intact.
- `registerWorkers` owns trusted tool selection, dispatch eligibility, handler serialization and owner route RPC. No agent-callable method can bind a role or edit a saved run.
- `workerHostContract.verifyWorkerCommit` receives only server-selected host paths and saved branch refs. Git runs without a shell; raw command errors never enter logs or RPC results.
- Start reconciliation preserves worker fields when retrying B1's writes. Worker persistence preserves independently updated lane fields.
- Strikes, time limits and full reconstruction are separate Spec B tickets. Questions and the owner's lane controls are described above and in [Starting a lane](lanes.md). Reported idle workers release running capacity; the one fix round rechecks and reserves the same cap before sending. Failed-record recovery remains B8 work; Resume leaves failed worker records reserved. Review writes preserve other saved worker/lane fields, and recovery-only display records grant no role tools or dispatch.

Tests use the pre-agreed Helper-core, tool-handler and SDK plugin-host seams, synthetic recorded Linear responses, temporary SQLite and local Git fixtures. The end-to-end fixture covers Start, Lead spawn, worker report, bound reviewer approval, verified integration and status delivery. Real provider startup, enrolled-host provisioning, live Linear delivery, process-kill recovery and visual/keyboard behavior remain Not proven.
